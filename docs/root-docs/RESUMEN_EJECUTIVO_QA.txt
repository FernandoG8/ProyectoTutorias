━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. RACE CONDITION EN CONTADOR DE CAMBIOS DE TUTOR
   ├─ Severidad: 🔴 CRÍTICA
   ├─ Probabilidad: ALTA (si hay >10 reasignaciones concurrentes)
   ├─ Impacto: Alumno puede reasignarse 3+ veces (violación de invariante)
   ├─ Causa: incrementarCambiosTutor() sin @Version o lock
   └─ Fix: Agregar @Version en Alumno + optimistic locking

2. CHECK-THEN-ACT EN VALIDACIÓN DE DUPLICADO
   ├─ Severidad: 🔴 CRÍTICA
   ├─ Probabilidad: MEDIA-ALTA (en asignaciones concurrentes)
   ├─ Impacto: DataIntegrityViolationException no manejada
   ├─ Causa: Validación no es atómica con save()
   └─ Fix: SERIALIZABLE isolation o catch DataIntegrityViolationException

3. DESINCRONIZACIÓN DE MAPA EN MEMORIA vs BD
   ├─ Severidad: 🔴 CRÍTICA
   ├─ Probabilidad: MEDIA (en procesos concurrentes largos)
   ├─ Impacto: Tutor sobrecargado (cargaActual > capacidadMax)
   ├─ Causa: Mapa local no se actualiza cuando OTRO proceso modifica tutores
   └─ Fix: Leer carga REAL de BD en cada selección, no del mapa

4. INCONSISTENCIA LEGACY/NUEVO EN SEMESTRE
   ├─ Severidad: 🔴 ALTA
   ├─ Probabilidad: MEDIA (con modificaciones futuras)
   ├─ Impacto: Queries retornan resultados inconsistentes
   ├─ Causa: Campo semestreAcademico (string) y semestre (entidad) desincronizados
   └─ Fix: Deprecar completamente semestreAcademico, migración SQL

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🟠 RIESGOS ALTOS IDENTIFICADOS (4)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

5. ALERTAS PERDIDAS EN CASO DE EXCEPCIÓN
   ├─ Severidad: 🟠 ALTA
   ├─ Impacto: Reasignaciones forzadas no se auditan
   └─ Fix: Guardar alertas ANTES de poder fallar

6. SIN VALIDACIÓN DE SEMESTRE VIGENTE
   ├─ Severidad: 🟠 ALTA
   ├─ Impacto: Posible modificación de datos históricos
   └─ Fix: Validar semestre.estaActivo() y semestre.estaVigente()

7. CONTADOR NO VALIDADO EN ASIGNACIONSERVICE
   ├─ Severidad: 🟠 ALTA
   ├─ Impacto: Inconsistencia entre flujos manuales y automáticos
   └─ Fix: Validar puedeReasignarse() en AsignacionServiceImpl

8. CARGA ACTUAL INCONSISTENTE DESPUÉS DE CLEANUP
   ├─ Severidad: 🟠 ALTA
   ├─ Impacto: Tutores con carga_actual desincronizada vs realidad
   └─ Fix: SIEMPRE recalcular después de cleanup

📊 INVARIANTES DE NEGOCIO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ CUMPLIDO:
  • Un alumno NO puede tener 2+ asignaciones en el MISMO semestre
  • tutorActual corresponde a la asignación más reciente
  • Capacidad de tutor se respeta (si no hay concurrencia)

⚠️  EN RIESGO:
  • Contador de cambios <= 2 (race condition possible)
  • Carga_actual = COUNT(asignaciones activas) (desincronización posible)
  • Tipo de asignación refleja origen correcto (no diferencia manual vs automático)
