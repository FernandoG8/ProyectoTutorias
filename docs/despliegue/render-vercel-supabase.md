# Deploy a Supabase (PostgreSQL) + Render (Backend) + Vercel (Frontend)

Esta guía prepara el backend (Spring Boot) y frontend (Vite/React) para correr en dev con MySQL/MariaDB y en prod con PostgreSQL (Supabase), desplegando en Render (backend) y Vercel (frontend).

## 1. Variables de entorno
- Copia `.env.example` y ajusta valores para dev/prod (no commitees secretos).
- Claves principales backend prod: `DB_URL`, `DB_USER`, `DB_PASSWORD`, `JWT_SECRET`, `APP_CRYPTO_KEY`, `CORS_ALLOWED_ORIGINS`, `PORT` (Render lo define), `SPRING_PROFILES_ACTIVE=prod`.
- Frontend: `VITE_API_BASE_URL` apuntando al backend público.
- Zona horaria sugerida: `TZ=America/Mexico_City`.

## 2. Supabase (PostgreSQL)
1) Crea proyecto en Supabase.
2) En Settings → Database copia la connection string Postgres.
3) Construye JDBC URL: `jdbc:postgresql://<host>:5432/postgres?sslmode=require` (usa el db name/host/port que dé Supabase).
4) Configura env vars para Render backend:
   - `DB_URL` = JDBC anterior
   - `DB_USER` = usuario Supabase
   - `DB_PASSWORD` = password Supabase
5) Flyway: al iniciar backend con profile `prod`, Flyway ejecuta migraciones (`db/migration`) contra Postgres.
6) Verifica en Supabase → SQL Editor que se crean tablas.

## 3. Backend en Render
1) Crear Web Service desde GitHub, root `backend`.
2) Build command: `./mvnw -DskipTests package`
3) Start command: `java -jar target/*.jar`
4) Env vars (Render dashboard):
   - `SPRING_PROFILES_ACTIVE=prod`
   - `PORT` (Render la inyecta)
   - `DB_URL` / `DB_USER` / `DB_PASSWORD`
   - `JWT_SECRET` / `APP_CRYPTO_KEY`
   - `CORS_ALLOWED_ORIGINS=https://<tu-frontend>.vercel.app`
   - `COOKIE_DOMAIN=<tu-dominio>` (opcional)
   - `TZ=America/Mexico_City` (sugerido)
5) Healthcheck: `https://<backend>/actuator/health` (Actuator habilitado por starter; también puedes exponer `/api/health` si lo agregas).
6) Logs: Render → Events.

## 4. Frontend en Vercel
1) Importa el repo en Vercel, root `frontend/tutoring-frontend`.
2) Build command: `npm ci && npm run build`
3) Output dir: `dist`
4) Env vars: `VITE_API_BASE_URL=https://<tu-backend>.onrender.com`
5) `vercel.json` incluye rewrite SPA → `index.html`.
6) Tras deploy, prueba login y llamadas reales.

## 5. Dev local
- Backend: usa `application-dev.yml` (MySQL/MariaDB). Env por defecto en `application-dev.yml`, override con `.env` si quieres.
- Frontend: `VITE_API_BASE_URL=http://localhost:8080` y corre `npm run dev` en `frontend/tutoring-frontend`.
- Flyway habilitado en dev.

## 6. Notas de compatibilidad
- Drivers: MySQL y Postgres están en `pom.xml` (runtime). JPA dialect por profile.
- Migraciones Flyway: se agregaron variantes para Postgres en `backend/src/main/resources/db/migration/postgresql/` (V2..V7) para evitar AUTO_INCREMENT/ENGINE y usar `GENERATED BY IDENTITY`, tipos TIMESTAMP/BOOLEAN/TEXT. Se mantienen las migraciones MySQL originales en `db/migration`.
- CORS configurable via `CORS_ALLOWED_ORIGINS`.

### Migraciones MySQL vs PostgreSQL
| Versión | Motivo de incompatibilidad MySQL→Postgres | Acción tomada |
| --- | --- | --- |
| V2__crear_tabla_semestre | AUTO_INCREMENT, ENGINE, DATE/TIMESTAMP defaults | Variante Postgres con BIGSERIAL, sin ENGINE, tipos estándar. |
| V3__crear_tablas_egresados_baja_definitiva | AUTO_INCREMENT, ENGINE | Variante Postgres con BIGSERIAL, sin ENGINE. |
| V4__crear_tabla_tutor_cambio_auditoria | AUTO_INCREMENT, ENGINE, LONGTEXT, logs_migracion insert no estándar | Variante Postgres con BIGSERIAL, TEXT, sin ENGINE ni logs_migracion. |
| V5__crear_tabla_usuarios_google_link | AUTO_INCREMENT | Variante Postgres con BIGSERIAL. |
| V6__add_google_refresh_columns | DATETIME, IF NOT EXISTS syntax MySQL | Variante Postgres con TIMESTAMP y guardas con DO $$ blocks. |
| V7__crear_tabla_export_jobs | MEDIUMTEXT | Variante Postgres con TEXT. |

Flyway ejecutará las de `db/migration/postgresql` cuando el datasource sea Postgres (configura `spring.flyway.locations=classpath:db/migration,classpath:db/migration/postgresql` si usas profiles separados; o deja ambas rutas y Flyway aplicará las nuevas por versión en entornos vacíos).

## 7. Smoke Tests esperados (ejecutar en entorno real)
- Backend: `GET /actuator/health` → 200 OK.
- Auth: login JWT con credenciales reales → obtiene cookies/headers; verify `Set-Cookie` flags Secure+SameSite=None.
- OAuth2 Google LINK → callback exitoso; usuario vinculado.
- OAuth2 Google DRIVE_CONNECT → obtiene refresh_token; exportación de archivo de prueba a Drive.
- Exportación individual (carrera/tutor) → archivo en Drive; sin error 403.
- Exportación masiva → procesa todos; sin duplicados de semestre ni fallos de parents; ZIP/reportes correctos.
- Frontend en Vercel consume backend en Render con `withCredentials=true`; CORS permitido.
